# CUDA Training Investigation: 2026-09-21

After the batch-size investigation, the user approved default microbatch and
effective batch 32 for CUDA tiny 2D and subsequently 16 for CPU tiny 2D. The
implementation resolves those defaults against the actual device, preserving
explicit saved values. MPS, 2.5D, 3D and other presets are unchanged. Earlier measurements below used their
stated explicit batch settings, not necessarily today's defaults.

## Configuration Failure

Commit `551005e` introduced both an exported `lr_scheduler.step_scope` field and
a scheduler parser that rejected that field. This was an export/reload contract
bug dating from scheduler support, not a consequence of the latest performance
changes. The exporter and parser now share the derived scope. Unknown options
and scopes inconsistent with the scheduler remain errors.

Reusing the actual saved configuration also exposed null, inapplicable
`context_slices` and JSON-list augmentation shapes. Null context is accepted;
augmentation tuples are restored and the new run's resolved patch geometry takes
precedence over previously exported augmentation geometry.

Regression coverage includes scheduler export/reload for all four scheduler
types and actual train/export/retrain workflows in 2D, 2.5D and 3D. The existing
requirement that exported settings be resolved is retained, including the new
decoded-source cache budget.

## Throughput

| Change | Batch | ms/step | patches/s |
| --- | ---: | ---: | ---: |
| Baseline, 64 MiB decoded cache | 4 | 104.69 | 38.21 |
| Experimental 512 MiB reader caches | 4 | 76.50 | 52.29 |
| Shared automatic cache and cheaper CPU copies/reductions | 4 | 60.02 | 66.65 |
| Same implementation, batch override | 8 | 65.69 | 121.79 |
| Experimental 512 MiB caches, one CPU thread | 4 | 38.45 | 104.04 |

The production change uses one shared, run-scoped decoded cache for planning,
training and validation. Automatic capacity is at most 10% of available RAM,
capped at 512 MiB, with a 64 MiB fallback when availability is unknown. It avoids
repeated decompression without eagerly loading an entire dataset. Explicit
`data_cache_mb=0` disables caching. Annotation repair has its separate budget.

Small CPU collation copies and validity reductions use NumPy instead of invoking
PyTorch's intra-op pool. Tensor values, transforms and loss validity rules are
unchanged. Neither the global CPU thread count nor the default batch size was
changed. The one-thread result is an experiment, not a shipped configuration;
changing an application's global pool could hurt its other workloads.

## CPU Versus CUDA With Current Code

Two sequential runs per device used the current optimized implementation, with
identical saved configuration, 128 x 128 patches, microbatch/effective batch 4,
512 MiB cache, 14 PyTorch CPU threads, zero workers, and reporting every five
steps. Each run warmed up for 100 steps and measured 300 steps. Execution order
was CPU, CUDA, CUDA, CPU. CPU hardware is an Intel Core i7-13700H; GPU and Python
environment are as listed above.

| Device | First run, ms/step | Second run, ms/step | Combined patches/s |
| --- | ---: | ---: | ---: |
| CPU, float32 | 129.88 | 157.95 | 27.79 |
| CUDA, mixed precision | 52.95 | 53.82 | 74.93 |

Combined throughput divides total patches by total measured time across both
runs. CUDA was approximately 2.70 times faster by this measure. CPU timings
varied more; these runs do not establish the cause of that variability.

This compares normal device-specific training, including the data pipeline,
augmentation, forward/backward passes, optimizer and reporting. It is not a
same-precision kernel comparison. Startup, validation, checkpointing and Java/UI
overhead are excluded. Training-library behavior was not changed for this test.

Reproduce each device in a separate process, replacing `cpu` with `cuda` and
using different output filenames for each run:

```bash
/home/carlos/micromamba/envs/ofm/bin/python -m benchmarks.profile_training \
  --config /path/to/model/config.json --device cpu --mode throughput \
  --warmup 100 --steps 300 --batch-size 4 --threads 14 \
  --cache-mb 512 --report-every 5 --output /tmp/unet-profile/cpu-1.json
```

Raw results are `comparison-{cpu,cuda}-{1,2}.json` in
`/tmp/jdll-cuda-profile-results`.

## Batch Size and VRAM Sweep

The same tiny, 128 x 128 configuration was measured with 50 warmup steps and 150
timed steps per run. Other controls remained fixed: zero workers, 14 CPU threads,
512 MiB decoded-source cache, AMP, balanced augmentation, and reporting every
five steps. Each requested batch was resolved without gradient accumulation.
The model and patch size were not increased.

| Batch | ms/step | patches/s | Peak allocated, MiB | Peak reserved, MiB | Sampled process peak, MiB |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 | 49.60 | 80.65 | 89.05 | 114 | 238 |
| 8 | 61.46 | 130.17 | 172.49 | 202 | 326 |
| 16 | 91.75 | 174.39 | 338.86 | 408 | 532 |
| 32 | 165.25 | 193.65 | 667.50 | 746 | 870 |
| 64 | 321.24 | 199.23 | 1325.66 | 1468 | 1592 |
| 32, repeat | 160.30 | 199.63 | 667.50 | 746 | 870 |

Allocated and reserved figures are exact PyTorch high-water marks including
warmup. Driver-visible process usage was sampled by `nvidia-smi` every 200 ms,
including CUDA overhead; these samples can miss short-lived peaks. All runs
used the same monitoring method. Process usage is not whole-device usage.
See [PyTorch's memory documentation](https://docs.pytorch.org/docs/main/notes/cuda.html#memory-management)
for the distinction between allocator statistics and driver-visible memory.

The main throughput gain is already present at batches 16-32. Batch 64 nearly
doubles process VRAM relative to 32 but adds only about 3% throughput in this
sweep. Repeating batch 32 after batch 64 reached 199.63 patches/s at the same
870 MiB peak, essentially matching batch 64. There is no evidence here that
filling 4 GiB would be worthwhile, so the sweep stops at this apparent plateau
rather than increasing memory use for its own sake.

The 4 GiB preset reference is a planning budget, not preallocated VRAM. Raising
`memory_fraction` alone would not raise batch 4 beyond its configured/effective
batch cap. An explicit experiment with batch 32 uses both:

```json
{
  "batch_size": 32,
  "effective_batch_size": 32
}
```

This changes the optimizer's effective batch. It is not guaranteed to preserve
training quality or time to convergence. Compare fixed patch budgets as well as
throughput: keeping the same optimizer-step count processes more patches with
a larger batch. No training-library defaults were changed by this sweep.

Raw results are `/tmp/jdll-cuda-profile-results/vram-batch*.json`, with companion
driver-memory samples. Reproduce using the CPU/CUDA comparison command above,
selecting CUDA, `--warmup 50 --steps 150`, the desired batch and `--monitor-vram`.

## CPU Batch Size Under a 6 GB RAM Budget

The CPU sweep uses the same i7-13700H, tiny 2D model, RGB 128 x 128 patches,
balanced augmentation, float32, 14 PyTorch CPU threads, zero workers and 512 MiB
source cache. Microbatch and effective batch match, with no accumulation.

Important limitation: two unrelated CPU-heavy Python jobs were discovered
running concurrently. They were not interrupted. This is a comparison under
the machine's current load, not an uncontended estimate of the CPU's maximum
throughput. Do not compare these absolute rates directly with the earlier
CPU/CUDA runs or assume this batch-size optimum applies to other CPUs.

| Batch | ms/step | patches/s | Peak process RSS, MiB |
| --- | ---: | ---: | ---: |
| 1 | 84.91 | 11.78 | 1438.13 |
| 2 | 110.73 | 18.06 | 1413.18 |
| 4 | 184.25 | 21.71 | 1537.85 |
| 8 | 264.14 | 30.29 | 1658.28 |
| 16 | 439.51 | 36.40 | 1949.35 |
| 32 | 1068.55 | 29.95 | 2275.45 |
| 64 | 2417.50 | 26.47 | 3033.17 |
| 16, repeat | 551.80 | 29.00 | 1881.41 |

Batches 1-32 used 30 warmup and 100 measured optimizer steps. Batch 64 used
20 warmup and 40 measured steps to limit the duration of its slower iterations.
RSS is the OS high-water mark for the entire benchmark process, including
startup, loaded libraries, source cache and training. It is not whole-machine
RAM use and excludes other processes. All tested sizes remain below 6 GB, but
larger batches are not automatically faster. The batch-16 repeat varied by
approximately 20% in throughput, preventing a reliable winner between 8 and 16.
The CPU default remained four during this investigation. The user subsequently
selected 16 as the CPU tiny-2D default. An uncontended comparison of 8, 16 and 32
is still needed to establish the best size on this machine. No universal optimum
or benefit from filling the 6 GB budget is established by these measurements.

Raw results are `/tmp/jdll-cuda-profile-results/cpu-ram-batch*.json`. Reproduce
with `--device cpu --warmup 30 --steps 100 --batch-size B --threads 14
--cache-mb 512 --report-every 5` and the same source configuration. CPU thread
defaults were not changed.

## Remaining Work

The short optimized operator trace measured about 5.56 ms of total CUDA kernel
work per optimizer step, substantially less than wall time. CPU preparation and
host dispatch remain important. CUDA event spans include dispatch gaps and
must not be mistaken for GPU busy time.

Batch 8 improves measured patch throughput substantially, but changes the
effective batch and potentially the amount of data seen per epoch. It remains an
explicit user choice. Exact distance targets took roughly 2-3 ms per step in
these profiles, so moving them to CUDA was not the first optimization priority.

Raw JSON, cProfile output and the operator trace from this investigation are
in `/tmp/jdll-cuda-profile-results` on the benchmark machine. They are temporary
artifacts; the findings and reproduction procedure are retained here.
